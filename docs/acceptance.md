# Приёмка в реальных харнессах

Используйте временный Git-проект с простой функцией и тестом. Подключите текущий CLI,
создайте задачу через `agent-system task new smoke` и привяжите к ней чат
(`agent-system task bind smoke`). Не используйте production-проект или личную память
для прогона.

1. В Claude Code проверьте обнаружение explorer, implementer, reviewer и поставляемых
   скиллов checkpoint, migrate-memory. Чужие скиллы проекта должны сохраниться.
   Explorer должен прочитать код, implementer —
   изменить функцию по контракту и проверить тест, reviewer — независимо проверить diff.
2. Убедитесь, что завершение этапа и результат сабагента не вызвали checkpoint.
   Явно вызовите скилл `checkpoint` и проверьте, что в `journal/` появился НОВЫЙ файл
   с результатом проверки и намеренно незавершённой работой, а прежние записи не изменились.
   Завершите исходную сессию без финального checkpoint; остановите фоновые записи.
3. Откройте тот же проект в Codex. Убедитесь, что он прочитал project memory, определил
   свой session id, привязался к задаче явной командой, прочитал весь task.md и журнал
   через `agent-system task journal [slug]` целиком и сверил git status.
   Проверьте три роли и доступность двух поставляемых скиллов.
   Отдельно проверьте, что два открытых чата на одной задаче пишут checkpoint
   одновременно и получают два разных файла, а не затирают запись друг друга.
4. Повторите перенос в обратном направлении без команды checkpoint. Проверьте, что
   завершение и смена харнесса не добавили checkpoint; новый харнесс сверяет Git
   с последней явной записью и не выдаёт несохранённый контекст за известный.
5. Зафиксируйте версии харнессов, фактически выбранные модели, результаты и ограничения.

Этот прогон выполняет человек или текущий агент отдельно от CLI. Нельзя считать
перечень имён, синтаксическую проверку TOML или ответ основной сессии доказательством
успешного запуска custom subagent. Отключённая сеть/отсутствие авторизации означают
«не проверено», а не успешную приёмку.

## Проверка хранения v1

Это дополнительные сценарии проверки, а не отчёт об их выполнении:

1. Одновременно запишите checkpoint в одну задачу из разных чатов с одинаковыми
   первыми восемью символами session id, затем из одной сессии с одним timestamp.
   Все записи должны остаться полными и различными. Имя имеет вид
   `<YYYYMMDDThhmmssZ>-<hash32>-<ordinal6>.md`, ordinal начинается с `000001`.
   Проверьте повтор эксклюзивной публикации при занятом имени и коллизии hash32.
2. Прочитайте смешанный журнал командой `agent-system task journal [slug]`:
   legacy `journal.md` первым, старые и новые записи в проверенном порядке.
   Проверьте старый session id с дефисом/цифрами, числовой ordinal больше 9,
   отказ на повреждённой записи и отсутствие конвертации или изменения старых файлов.
   Проверяется детерминированный порядок показа; причинный порядок между машинами
   по timestamp не заявляется.
3. Запустите конкурентные `bind`/`unbind` одного session id и повторите с `--force`:
   операции должны проходить под одним per-session OS `flock`. Прерывание владельца
   должно освободить OS-блокировку; разные session id не мешают друг другу.
4. Два конкурентных `task new` с одним slug создают только одну задачу. После сбоя
   между резервированием каталога и записью `task.md` остаток обнаруживается как
   ошибка; повторная команда не перезаписывает его и не удаляет автоматически.
5. Session id проверяется без обрезки; пробелы, новые строки, `.` и `..` отвергаются,
   как и служебные `.locks`/`.agents-<32 lowercase hex>`.
   Checkpoint с явным slug отвергает отсутствующую или завершённую задачу до записи;
   завершённую сначала явно возобновляют. `--stage` принимает только полный шаблон
   `[A-Za-z0-9][A-Za-z0-9._-]{0,63}`, отвергая в том числе `#` и многострочный текст.
6. `bind` к другой задаче сохраняет legacy `ACTIVE`; соответствующий bind снимает
   его только без `LOCK`. При `LOCK` оба файла остаются с предупреждением о проверке
   неактивности старой сессии перед ручным удалением `LOCK` и повторным bind.
   Оба legacy-пути остаются gitignored до миграции.

## Результат локальной попытки, 2026-09-09

Автоматические проверки: 70 тестов проходят, включая 21 новый CLI-сценарий;
проверка generated drift и синтаксиса Bash проходит.

Реальный прогон пока не выполнен. Claude Code 2.1.266 при запуске explorer завершился
с `Not logged in · Please run /login`. Codex CLI 0.149.0 не смог инициализировать
app-server из-за ограничений доступа к локальной state database. Эти результаты
не подтверждают и не опровергают загрузку установленных ролей. После входа в Claude
и запуска вне этих ограничений нужно выполнить сценарий выше.

## Проверка стабилизации v1, 2026-09-11

Автоматические проверки выполнены в изолированной копии: **164 теста прошли**,
включая 23 сценария безопасности и конкуренции. Проверка generated drift чистая.
Проверены частичная запись и отказ fsync, читатель до публикации, одинаковые имена,
одновременные new/bind, освобождение flock после завершения процесса, симлинки
в родителях и файлах, повреждённые метаданные и чтение legacy-журналов.

Живой прогон — временный Git-проект с собственной временной памятью. Codex CLI
**0.149.0** (модель основной сессии `gpt-5.6-sol`) успешно выполнил bind, явный checkpoint и task journal новой версией CLI.
Наличие маркера в журнале проверено отдельно от ответа модели. После `exec resume`
оба значения `CODEX_THREAD_ID` и `CODEX_SESSION_ID` сохранились; новый чат получил
другие значения, прочитал прежнюю запись и не создал новый checkpoint. Первый
прогон выбрал старую команду из login-shell PATH; повтор с абсолютным путём к
проверяемому CLI прошёл. Приёмка должна всегда проверять используемый executable.

**Именованные роли Codex не засчитаны:** в доступной этому прогону схеме spawn_agent
нет параметра выбора конфигурации роли. Вызовы с task_name="explorer"/"implementer"/
"reviewer" доказывают только создание подзадач с этими именами. Требуется отдельный
прогон, где можно подтвердить загрузку именно установленных конфигураций.
В окружении также есть предупреждения о некорректных глобальных файлах ролей;
они не изменялись в рамках этой работы.

Claude Code **2.1.266** сообщает `loggedIn: false`. Живой прогон Claude, проверка его
resume и переключение между двумя харнессами остаются **не выполнены** до входа.
Это ограничение приёмки; автоматические тесты не заменяют эти сценарии.

# Операционный контракт

Этот файл читают оба харнесса. Правила здесь применимы и к Claude Code, и к Codex.

---

## 1. Состояние: два уровня

```text
.agents/memory/                знание о проекте    живёт дольше задач
.agents/state/tasks/<slug>/    состояние задачи    умирает вместе с задачей
```

**Память проекта** — как работать с этим репозиторием: где что лежит, что долго
собирается, где грабли в тестах, какие соглашения приняты. Один факт — один файл.
Лежит вне git проекта, общая для всех веток и worktrees.

**Состояние задачи** — два файла, оба коммитятся в ветку задачи и **общие для обоих
харнессов**. Отдельных версий под Claude и Codex не бывает.

| Файл | Что содержит |
|---|---|
| `task.md` | контракт задачи: goal, scope, acceptance criteria, non-goals, constraints |
| `journal.md` | решения, результаты, тупики, незавершённая работа, состояние дерева |

Отдельного снимка состояния нет. Журнал читается целиком — проекция не нужна.

---

## 2. Начало сессии

```text
1. Прочитать .agents/state/ACTIVE
2. Проверить, что задача валидна (см. ниже)
3. Прочитать task.md и journal.md ЦЕЛИКОМ
4. Проверить фактическое состояние репозитория: git status, diff
```

**Разрешение активной задачи.** `ACTIVE` содержит slug внутри `tasks/` — это
authoritative локальный указатель, ветка лишь подсказка.

```text
ACTIVE существует?
├── да  → валидировать
└── нет → найти задачу со status: active и branch == текущая ветка
          ├── ровно одна → записать ACTIVE
          └── ноль или несколько → автоматический выбор НЕ делать, спросить
```

**Валидация обязательна.** `ACTIVE` не обновляется сам при `git checkout`. Проверить:
существует ли `tasks/<slug>/task.md`, совпадает ли `id`, `status: active`, и совпадает ли
`branch` из `task.md` с текущей веткой.

При расхождении — **не загружать задачу молча**. Перезапустить discovery и сообщить
о расхождении. Загрузить чужую задачу хуже, чем не выбрать никакую.

В detached HEAD или при пустом `branch` автоматического совпадения нет — задача
выбирается явно.

## 3. Checkpoint

Состояние накапливается **по ходу работы**, а не сериализуется в конце. Сессия может
оборваться на лимите или краше, и хода на сохранение уже не будет.

Чекпойнт делает **оркестратор после интерпретации результата**, не сабагент:

```text
сабагент вернул результат → main оценил → результат принят → CHECKPOINT → следующий этап
```

Правило действует и для работы main без сабагентов, и при существенном отклонении
результата. Длинные этапы разбиваются на промежуточные чекпойнты.

**Следующий этап начинается после успешной записи.** Если запись упала, чекпойнт
сохранённым не считается — иначе вы работаете в уверенности, что этап сохранён, а его нет.

### Что писать

Критерий один:

> Всё существенное для продолжения, что **нельзя восстановить из файлов репозитория**.

Сюда входит:

- новое решение и **принятое намерение**, включая решение о следующем шаге;
- важный результат, отвергнутый подход **с причиной**;
- завершённый кусок реализации, существенный blocker;
- результат проверок, включая «не запускались»;
- **состояние рабочего дерева: чисто или грязно и почему.**

Намерение пишется наравне с результатом. Решение «сначала проверить совместимость
миграции на старых данных, потом реализовывать» не оставляет следа в коде — если его
не записать, оно не восстановится ниоткуда.

Состояние дерева выделено намеренно: новая сессия увидит изменения в `git status`,
но не поймёт, брошены они или намеренно оставлены на середине.

**Чего не писать:** полного пересказа всего состояния каждый раз. Записывается дельта.
Журнал, где девять десятых повторов, перестают перечитывать.

### Формат записи

```md
## 2026-09-09 18:20 — Claude / implementer

Tried replacing the legacy cache through the repository abstraction.
Rejected: the abstraction does not expose atomic compare-and-set,
which the current synchronization path requires.
```

Timestamp — для удобства чтения, идентификатором не является: порядок задаёт сам файл.

## 4. Переключение харнесса

Явная операция — скилл `checkpoint` (`.agents/skills/checkpoint/`). Отдельного «сбора
состояния» нет: состояние уже накоплено. Переключение — это проверка полноты и остановка.

---

## 5. Делегирование

Стадии определяются семантическими сигналами, а не ощущением.

**TRIVIAL** — нет изменения публичного контракта, нет schema/миграции, нет auth и
security-логики, нет concurrency и распределённого состояния, нет cross-component
инварианта, паттерн очевиден.
→ `main или implementer → verification`. Reviewer опционален.

**NORMAL** — default, когда задача не очевидно тривиальна и не содержит complex-сигналов.
→ `explorer если нужен → implementer → reviewer`.

**COMPLEX** — изменение публичного API или протокола, миграция схемы, риск потери данных,
auth и permissions, concurrency, распределённое состояние, cross-service контракт,
изменение архитектурной границы, высокая неоднозначность, новая стратегия реализации.
→ `explorer → планирование → implementer → reviewer`.

Количество изменённых файлов — **слабый** сигнал. Переименовать 20 сгенерированных файлов
может быть тривиально; поменять строку в логике авторизации — нет.

**При неуверенности — NORMAL.** Явный override пользователя разрешён в обе стороны.

---

## 6. Fix loop

```text
implement → review → fix → review
```

По умолчанию максимум 2–3 корректирующих раунда. После этого main **диагностирует причину**
несходимости, а не эскалирует автоматически по числовому лимиту:

```text
неясное требование        → спросить пользователя
техническая неизвестность → explorer
implementation thrashing  → остановить цикл и суммировать
фундаментальная проблема  → вернуться к планированию
```

Отдельного постоянного оркестратора нет: main-сессия и есть оркестратор.

## 7. Завершение задачи

Завершение — **шаг выпуска знаний, а не удаление каталога**. Без него самые дорогие
находки, добытые в тупиках, исчезнут вместе с журналом.

Пройти журнал и разложить:

| Что | Куда |
|---|---|
| решение по коду и архитектуре, которое должны знать люди | документация проекта, в git |
| как работать с этим репозиторием | `.agents/memory/` |
| ход конкретной задачи | никуда — умирает с задачей |

Третья строка не менее важна первых двух: если выпускать всё, память станет вторым
журналом и перестанет быть полезной.

Затем: `status` → `done`/`abandoned`, очистить `ACTIVE`, если он указывает на эту задачу,
и удалить состояние задачи перед merge — либо перенести в `.agents/state/archive/<slug>/`,
если история осознанно ценна.

**Важно:** после squash промежуточные коммиты в историю `main` не попадают, а удалённая
ветка и PR не являются хранилищем. Default означает осознанную потерю журнала. Нужна
история — выбирайте archive **до** удаления.

---

## 8. Гигиена коммитов

**Никогда не использовать `git commit -a` и `git add -A`. Пути под индекс добавляются явно.**

Типичный сбой: `git commit -am "feat: ..."` заметает в фичевый коммит заодно `journal.md`,
и дальше это едет в squash и в `main`.

Правки в `.agents/agents/` и `.agents/skills/` не коммитить молча — это канон, за ним
тянется регенерация и проверка drift. Состояние задачи коммитится свободно, но отдельными
коммитами от кода.

---

## 9. Инварианты

- **Одна активная задача на рабочее дерево.**
- **Одна main-сессия на рабочее дерево одновременно**, включая две сессии одного харнесса.
  Разные фичи — разные worktrees. `.agents/state/LOCK` — advisory-пометка: увидел чужой,
  выясни чей, а не вытесняй. Одновременный старт она не предотвращает.
- **Canonical task state пишет только main.** Параллельным implementer назначаются
  непересекающиеся области; перед checkpoint запись прекращают и сабагенты.
- **`runs.jsonl` никогда не является каноническим состоянием.**

---

## 10. Параллельная работа

Над разными фичами — через git worktrees, по одному харнессу на дерево:

```text
repo/              → Claude, feature A
../repo-billing/   → Codex,  feature B
```

`ACTIVE`, `LOCK` и симлинк памяти gitignored и потому у каждого дерева свои; состояние
задачи коммитится и живёт на своей ветке. Определения агентов и скиллов версионируются
веткой — правка на ветке A не видна на ветке B до мержа.
